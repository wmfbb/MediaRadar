## 1. Что строим

**МедиаРадар** — платформа региональной медиа-разведки. Она:

1. **Собирает** публикации из региональных онлайн-СМИ, официальных порталов, Telegram-каналов и чатов, VK, YouTube, форумов, а также статистические показатели (Росстат, ЕМИСС, ЦБ и т.п.) — по расписанию, с ретро-загрузкой «задним числом».
2. **Обрабатывает**: чистит, убирает дубли и перепечатки, извлекает персон/организации/места (NER), оценивает тональность, определяет тему и территорию, строит краткие саммари, группирует публикации в «сюжеты».
3. **Показывает**: портал с умной лентой и фильтрами, дашборды, графики, карты, страницы персон/организаций/сюжетов, автоматические сводки и обзоры «на лету».
4. **Сообщает**: алерты по ключевым словам/персонам/аномалиям (Telegram, email), регулярные дайджесты, отчёты PDF/Excel/PowerPoint.
5. **Продаётся** как SaaS: тенанты = регионы/клиенты, роли, тарифы, оплата через ЮKassa, публичный API.

Первый тенант — **Алтайский край** (ядро — Барнаул, далее города края, сёла/посёлки — опционально). Движок сразу проектируется как универсальный: другой регион или страна подключаются настройкой, а не переписыванием кода.

## 2. Решения

### 2.1 Принято вместе с владельцем

| # | Тема | Решение |
|---|------|---------|
| 1 | Бэкенд | Node.js (TypeScript) |
| 2 | Модель продукта | Полный SaaS с мультитенантностью — **но поэтапно** (схема и изоляция данных закладываются в Фазе 0, остальное включается по фазам) |
| 3 | AI/NLP | Базовый режим — CPU-гибрид (локальный русский NLP + LLM по API). Режим «с GPU, всё локально» — опция. **Обязателен универсальный AI Gateway**: подключение любых моделей (GigaChat, YandexGPT, Qwen, DeepSeek, OpenAI-совместимые, Anthropic, Gemini, Ollama/vLLM и т.д.) из админки, с маршрутизацией и бюджетами |
| 4 | Telegram | Веб-превью `t.me/s/…` + MTProto (служебный аккаунт) для чатов и глубокой истории. Bot API — алерты и бот-интерфейс |
| 5 | Политика контента | Гибрид по типу источника (гос. порталы — полный текст, остальные — заголовок + лид + ссылка на оригинал). **Управляется настройками** на уровне платформы/тенанта/источника |
| 6 | Бренд | «МедиаРадар» + бренд региона (white-label: логотип, цвета, домен тенанта; первый — «Алтай.Медиа») |

| 8 | Ретро-сбор | По умолчанию 1 год; глубина/лимиты/приоритеты настраиваются (платформа → тенант → источник) |
| 9 | Сроки | Дедлайна нет — «делаем правильно», строго по фазам |

| 11 | Управление | «Максимальный контроль»: супер-админка + реестр типизированных настроек с аудитом |

| 13 | Исходные ресурсы | У владельца пока нет сервера, домена, ключей AI, Telegram-учёток, юрлица под платежи → всё разрабатывается на моках/локально, реальные ключи подключаются по мере фаз (см. раздел 7) |

## 3. Принципы разработки

1. **Данные важнее интерфейса.** Сначала надёжный сбор и корректная модель данных, потом красивые экраны поверх реальных данных.
2. **Всё идемпотентно и повторяемо.** Любую стадию обработки можно запустить заново (смена модели, исправление парсера) без дублей и потерь.
3. **Дешёвое — вперёд, дорогое — по необходимости.** Сначала RSS/sitemap/статический HTML, браузер — только когда нужен; сначала локальные модели, LLM — когда уверенность низкая или фича премиальная.
4. **Каждое поведение — настройка, а не константа.** Политика контента, глубина сбора, расписание, пороги, маршруты AI — в реестре настроек с областью действия, валидацией, историей и откатом.
5. **Безопасность по умолчанию.** Изоляция тенантов на уровне БД (RLS), защита от SSRF в сборщике, недоверие к скрапнутому контенту (в т.ч. от prompt injection).
6. **Измеряем качество.** Размеченные эталонные выборки для NER/тональности, фикстуры HTML для парсеров, метрики здоровья источников — до, а не после запуска.
7. **Сопровождаемость без программиста.** Автоматизация деплоя, бэкапы с проверкой восстановления, алерты о сбоях в Telegram, инструкции-ранбуки.

## 5. Фазы подробно

### Фаза 0 — Фундамент

**Состав**
- Монорепозиторий (структура — [ARCHITECTURE §15.4](ARCHITECTURE.md)); `index.html` переезжает в `prototype/` как эталон дизайна.
- `make dev` поднимает всё локально (Postgres, Redis, API, web, worker; MinIO добавится в Фазе 5, когда появятся файлы отчётов).
- Схема БД ядра: тенанты, пользователи, членства, роли/права, настройки, аудит, источники, материалы (минимум); **RLS-политики** и тесты изоляции.
- Аутентификация: регистрация/вход (argon2id, cookie-сессии), восстановление пароля, TOTP-2FA для админ-ролей; серверный слой авторизации (permissions → roles).
- **Реестр настроек** (типизированные настройки с областями `платформа → тенант → источник → пользователь`, валидация Zod, история, аудит) — основа для «максимального контроля».
- Дизайн-токены и библиотека компонентов из прототипа (`packages/ui`), светлая и тёмная темы, каркас приложения (сайдбар, топбар, ⌘K).
- Перенос 9 экранов прототипа на Next.js, подключённых к API на **сидовых синтетических данных** (генератор правдоподобных материалов).
- CI (GitHub Actions): lint, typecheck, unit/integration-тесты, сборка образов.
- Наблюдаемость: структурные логи, `/healthz`, метрики Prometheus.

**Готово, когда**: свежий клон + `make dev` → рабочий портал с демо-данными; вход по логину; пользователь тенанта A не может получить данные тенанта B (автотест на каждую таблицу); CI зелёный.

**Статус: реализовано.** Как запустить и что внутри — [DEVELOPMENT.md](DEVELOPMENT.md). Что проверено и чего нет:

- Проверено автотестами (405 штук: ядро 23, права 32, настройки 12, БД/RLS 161, API 149, воркер 4, UI 11, web 13) и e2e в браузере (12 сценариев: вход, возврат на страницу, ABAC по темам, 2FA от включения до отключения, тема, ⌘K, платформенная админка, живой поток по WebSocket).
- Изоляция тенантов: для каждой таблицы схемы тест подтверждает, что тенант A не видит и не меняет строки B; тест «все таблицы классифицированы» не даст добавить таблицу без политики.
- **Не проверено здесь**: сборка Docker-образов и production-compose (в среде разработки нет Docker-демона; шаги Dockerfile повторены вручную, YAML проверен `docker compose config`; первую реальную проверку выполнит job `docker` в CI), Caddyfile.
- **Заглушки до своих фаз**: сбор материалов (Фаза 1; воркер лишь публикует синтетические материалы при `DEMO_LIVE=true`), формирование отчётов PDF/Excel (Фаза 5), оплата ЮKassa (Фаза 8), AI-дискавери и NER/тональность по-настоящему (Фазы 3 и 6) — в интерфейсе это помечено, API отвечает честным `implemented: false` / 501.
- Отличия от плана: путь WebSocket — `/v1/ws`; таблица `articles` пока без партиций (Фаза 1); MinIO в dev-окружении появится в Фазе 5.

### Фаза 1 — Сбор данных

> **Решения владельца для облегчённой версии (приоритет над списком ниже).** Сначала — ядро: RSS/Atom + HTML-списки по селекторам; **15–20 реальных источников** Алтайского края; Live-режим (новые материалы сразу попадают в ленту по WebSocket); хранение **минимума** (заголовок, короткий лид, ссылка, дата, источник, ссылка на картинку — картинку подтягиваем по ссылке, при недоступности показываем свою заглушку; копии изображений хранятся только для графиков и данных). Каждая запись имеет собственный неизменный ID. **Удаление на источнике:** запись никогда не удаляется у нас — помечается «удалено на источнике» с временем обнаружения и доказательством (код ответа, время проверки); проверяются материалы последних 7 суток по расписанию. Откладывается: JS-рендеринг, Telegram, студия парсеров, S3, SimHash, прокси-пулы.

**Состав**
- **Фреймворк коннекторов** (`discover → fetch → parse`), единый контракт, тесты на фикстурах HTML.
- Коннекторы: RSS/Atom, sitemap (в т.ч. news-sitemap), статический HTML (list+article), **JS-рендеринг (пул Playwright, изолированный контейнер)**, Telegram web-preview.
- **Студия парсеров**: декларативный JSON-конфиг (селекторы, пагинация, форматы дат, очистка), пробный прогон с превью, версии конфигов, откат. Автоопределение селекторов (эвристики + Readability; LLM-подсказка — после Фазы 3).
- **Планировщик**: адаптивная частота (по реальному темпу публикаций), jitter, backoff при ошибках, лимиты на домен, соблюдение robots.txt, автопауза и эскалация нездоровых источников.
- **Безопасный сборщик**: защита от SSRF, лимиты размера/времени, кэш `ETag/Last-Modified`, прокси-пулы (абстракция), понятный User-Agent.
- **Нормализация**: канонический URL, даты (часовые пояса РФ, «вчера в 14:30»), очистка HTML, изображения → S3 + миниатюры, язык, автор, OpenGraph/JSON-LD.
- **Дедупликация**: URL → хэш контента → SimHash (перепечатки) в скользящем окне.
- **Ретро-сбор**: отдельная очередь с низким приоритетом и лимитами; глубина берётся из настроек.
- Админка: реестр источников, запуск «сейчас», логи прогонов, метрики здоровья, монитор очередей (Bull Board + собственные экраны).
- Стартовый реестр **20–30 проверенных источников** Алтайского края (процедура верификации — ниже, §7 и PRODUCT_SPEC §11).

**Готово, когда**: 7 суток подряд сбор по 20+ источникам без ручного вмешательства; доля успешных прогонов ≥ 95%; дубль-ставка < 2% (по контрольной выборке); при ломающемся парсере приходит алерт, остальные источники не страдают.

### Фаза 2 — Лента, поиск, реалтайм

**Состав**: API материалов с курсорной пагинацией; полнотекстовый поиск (Postgres FTS, русская морфология, `pg_trgm` для опечаток); фасеты и счётчики; сохранённые фильтры; фильтры в URL (делимся ссылкой); страница материала; WebSocket-поток «в реальном времени» (Redis pub/sub, подписка по сохранённому фильтру); базовый **публичный портал** (SSR, SEO-разметка, sitemap.xml, OpenGraph); соблюдение `content_policy` при отдаче текста.

**Готово, когда**: p95 поиска < 300 мс на синтетической базе 1 млн материалов; новая публикация появляется в ленте < 15 с после сохранения; публичные страницы проходят проверку SEO и доступности.

### Фаза 3 — AI Gateway и NLP

**Состав**
- **AI Gateway** ([ARCHITECTURE §8](ARCHITECTURE.md)): реестр провайдеров и моделей, маршрутизация задач с фолбэками, бюджеты/квоты, реестр промптов с версиями, кэш, учёт расхода. Адаптеры: OpenAI-совместимый (DeepSeek, Qwen, OpenRouter, vLLM, Ollama…), GigaChat, YandexGPT, Anthropic, Gemini, **универсальный декларативный HTTP-адаптер** для любой нейросети без правки кода.
- **NLP-сервис (Python)**: NER (Natasha/Slovnet и др.), тональность (русские BERT-модели + калибровка на 5 градаций), эмбеддинги (мультиязычные модели на CPU/ONNX), ключевые слова.
- **Конвейер обработки** (BullMQ, стадии идемпотентны): язык → NER → связывание сущностей с каноническими (персона/организация/место, алиасы) → гео-привязка (ГАР/ОКТМО/OSM) → тональность → темы (классификация по таксономии) → саммари → ключевые слова → эмбеддинги → кластеризация в сюжеты.
- **Эталонные выборки и оценка**: ~500 размеченных материалов (тональность, NER, темы) → автоматический замер качества при смене модели/промпта.
- Админка AI: провайдеры, модели, маршруты, промпты, бюджеты, журнал вызовов, A/B и «теневой» режим новой модели.

**Готово, когда**: пайплайн обрабатывает поток без накопления очереди; метрики качества на эталонной выборке выше целевых порогов (задаются по итогам первичной разметки, цель: NER F1 ≥ 0,85 на персонах/организациях, macro-F1 тональности ≥ 0,70); принудительный отказ провайдера → автоматический фолбэк; бюджет тенанта реально останавливает расход.

### Фаза 4 — Аналитика

**Состав**: агрегаты (по дням/часам × источник × тема × гео × тональность × сущность); семантический слой запросов (белый список измерений и метрик, без произвольного SQL); дашборды с настраиваемыми виджетами; страницы **персон, организаций, источников, сюжетов, территорий**; карта-хороплет по районам; «Share of Voice», индекс тональности, тепловая карта «тема × источник», облако тем, граф связей, «кто кого цитирует», скорость публикации, оригинальность; детекция аномалий и всплесков; экспорт CSV/XLSX.

**Готово, когда**: все графики прототипа питаются реальными данными; ответ виджета < 1 с на горизонте 90 дней; числа на дашборде совпадают с контрольными SQL-выгрузками.

### Фаза 5 — Алерты, отчёты, рассылки

**Состав**: движок правил (ключевые слова, сущности, темы, пороги, аномалии, комбинации) с уровнями важности и подавлением дублей; каналы: Telegram-бот, email, web-push (SMS — по запросу); дайджесты (утро/неделя) по интересам; **конструктор отчётов** (блоки: текст, график, таблица, KPI, AI-нарратив) → HTML → **PDF (Playwright)**, **XLSX (exceljs)**, **PPTX (pptxgenjs)**; расписание и доставка; фирменное оформление тенанта; **AI-автообзоры с обязательными ссылками на материалы** (числа считает код, LLM только пишет текст), шаг ручной проверки; Telegram-бот как второй интерфейс (поиск, подписки, сводки).

**Готово, когда**: алерт приходит < 2 минут после публикации; PDF-отчёт читается без правок вёрстки; каждое утверждение автообзора имеет ссылку на источник.

### Фаза 6 — Расширение источников

**Состав**
- **AI-дискавери** ([PRODUCT_SPEC §11](PRODUCT_SPEC.md)): ТЗ → поисковые запросы и обход каталогов → классификация → проверка «живости» и «парсимости» → рейтинг авторитетности → очередь кандидатов на утверждение → автогенерация конфига → ретро-сбор.
- **Территориальное расширение**: ядро (Барнаул) → города → районы → населённые пункты, уровни включаются настройкой.
- **MTProto-коннектор** (чаты/каналы, служебный аккаунт; псевдонимизация авторов), VK API, YouTube Data API, адаптеры форумов.
- **Показатели (индикаторы)**: временные ряды из Росстата/ЕМИСС/ЦБ/профильных ведомств (агро, пищепром, топливо) — отдельная модель данных рядом с материалами.

**Готово, когда**: по ТЗ «Алтайский край» система выдаёт ≥ 150 кандидатов с обоснованием и рангом, из которых ≥ 70% отвечают «живой + парсится»; показатели отображаются на графиках рядом с динамикой публикаций.

### Фаза 7 — Полная мультитенантность и роли

**Состав**: кастомные роли и права (Enterprise), ограничение по темам/территориям/группам источников (ABAC), мастер онбординга тенанта (регион → отрасли → пресет источников), white-label (домен, логотип, цвета, шаблоны писем), полная супер-админка (тенанты, глобальный каталог источников, флаги функций, имперсонация с аудитом, объявления), журнал аудита с поиском.

**Готово, когда**: новый тенант создаётся за < 10 минут без участия разработчика; матрица прав покрыта автотестами «роль × действие».

### Фаза 8 — Биллинг и тарифы

**Состав**: тарифы и **entitlements** (лимиты источников/материалов/пользователей/AI-токенов, флаги функций); учёт использования; машина состояний подписки (trial → active → past_due → grace → suspended → canceled); платёжные провайдеры за интерфейсом (тестовый провайдер; **ЮKassa**: платежи, сохранение способа оплаты и автоплатежи, вебхуки с перепроверкой статуса, **чеки 54-ФЗ**, возвраты, СБП); дожим неудачных списаний; апгрейд/даунгрейд с пересчётом; промокоды и дополнительные пакеты (AI-токены); счета и акты для юрлиц (банковский перевод; ЭДО — позже); редактор тарифов в админке.

**Готово, когда**: полный цикл «оплата → доступ → продление → неуспешное списание → приостановка → возобновление» проходит в тестовом режиме ЮKassa; вебхук, пришедший дважды или в неправильном порядке, не ломает состояние.

### Фаза 9 — Расширение платформы

**Состав**: публичный API (ключи, лимиты по тарифу, OpenAPI, SDK, исходящие вебхуки); достоверность и маркировка (первоисточник, расхождения, подозрительные вбросы); **второй регион** как доказательство мультирегиональности; i18n (RU + EN), профиль GDPR (согласия, экспорт и удаление данных, срок хранения); PWA.

### Фаза 10 — Усиление и запуск

**Состав**: внешний пентест и устранение замечаний; нагрузочные тесты (k6); учения по восстановлению из бэкапа; ранбуки; юридические документы (политика ПДн, оферта, условия использования; **проверка юристом**); пилоты с 2–3 клиентами; финальная настройка мониторинга.

## 8. Риски и меры

| Риск | Вероятность / влияние | Меры |
|------|------------------------|------|
| Сайты блокируют сбор (антибот, Cloudflare, капчи) | Выс. / Сред. | Вежливый сбор (лимиты, robots.txt, понятный UA), кэш-заголовки, RSS/sitemap в приоритете, прокси-пулы как опция; при капче источник получает статус «требует внимания», а не обходится «в лоб»; **paywall не обходим** |
| Авторские права на перепечатку | Средн. / Выс. | Политика «выжимка + ссылка на оригинал» по умолчанию, полный текст — только для гос. источников и источников с договорённостью; настройки по источнику; юрист в Фазе 10 |
| Блокировка Telegram-аккаунта при MTProto | Выс. / Средн. | Отдельный служебный аккаунт, человеко-подобные лимиты, обработка FLOOD_WAIT, основной режим — веб-превью, MTProto только там, где нужно |
| Персональные данные (чаты, комментарии, NER-персоны) | Средн. / Выс. | Псевдонимизация авторов чатов; ограничение хранения; публичные персоны отдельно; реестр обработки ПДн; уведомление РКН; серверы в РФ |
| «Дрейф» вёрстки — парсеры ломаются | Выс. / Средн. | Дрейф-детекция по заполненности полей, фикстуры, алерты, быстрый откат конфига, AI-подсказка новых селекторов |
| Стоимость LLM | Средн. / Средн. | Каскад «локальная модель → LLM»; кэш по хэшу контента; бюджеты на тенанта; саммари лениво/только для важного |
| Качество русского NLP (сарказм, региональные имена, омонимия) | Выс. / Средн. | Эталонные выборки, калибровка на наших данных, словари алиасов региона, ручное слияние сущностей в админке |
| Утечка данных между тенантами | Низк. / Критич. | RLS на уровне БД, тесты на каждую таблицу, отдельные роли БД, ревью политик |
| Галлюцинации в автообзорах | Средн. / Выс. | Числа считает код; текст строго по найденным материалам с обязательными ссылками; шаг ручной проверки; маркировка «создано ИИ» |
| Prompt injection из скрапнутых страниц | Средн. / Средн. | Контент — это данные, а не инструкции: разделители, схемы вывода, запрет инструментов/ссылок из контента, валидация ответов |
| Зависимость от одного AI-провайдера | Средн. / Средн. | AI Gateway, фолбэки, локальные модели как запасной вариант |
| Недоступность внешних репозиториев (npm, Docker, HuggingFace) из РФ | Низк. / Средн. | Зеркалирование образов и моделей в своё хранилище, lockfile, закреплённые версии |
| «Фактор программиста» (владелец не программист) | Выс. / Выс. | Деплой одной командой, бэкапы, мониторинг с уведомлениями в Telegram, ранбуки, подробная документация, всё конфигурируется из админки |
| Лицензии моделей и данных | Средн. / Средн. | Проверка лицензий каждой модели/словаря до использования (коммерческое использование!); OSM — атрибуция (ODbL) |
| Законодательные требования к агрегаторам | Низк. / Средн. | При аудитории свыше порога (см. ст. 10.4 149-ФЗ о новостных агрегаторах) — обязанности владельца агрегатора; отслеживать вместе с юристом |

## 9. Открытые вопросы (ответы можно давать по ходу работы)

По каждому есть рабочее допущение — оно будет использовано, пока не придёт другое решение.

1. **Таксономия тем.** В прототипе 7 секторов (агро, топливо/энергия, госуправление, пищепром, город/ЖКХ, экономика, общество). Допущение: это стартовый пресет, тенант может править/расширять; внутри — иерархия.
2. **Тональность.** Допущение: 5 градаций как в прототипе, считаем скор −1…+1; «тональность по сущности» (отношение к конкретной персоне/организации) — отдельно.
3. **Публичный портал.** Допущение: часть ленты (заголовок + лид + ссылка) открыта без регистрации для SEO; аналитика и фильтры — по регистрации/тарифу. Это настраивается на тенанте.
4. **Тарифы.** Допущение: берём сетку FREE / STARTER / PRO / ENTERPRISE из прототипа с теми же ценами как плейсхолдером; финальные цифры и лимиты — отдельное решение.
5. **Каналы алертов.** Допущение: Telegram + email + web-push в Фазе 5; SMS — по запросу (нужен SMS-провайдер).
6. **Языки и юрисдикции следующих рынков.** Нужны ли в ближайший год Казахстан/Беларусь/другие? Допущение: нет, закладываем только архитектуру.
7. **Брендирование региона.** Допущение: «Алтай.Медиа» — первый тенант с собственным доменом.
