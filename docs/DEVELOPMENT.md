# МедиаРадар — руководство разработчика

Как запустить проект, где что лежит и как не сломать изоляцию тенантов. Состояние: **Фаза 0 выполнена, Фаза 1 и Фаза 3 — в облегчённом виде** (см. [PLAN.md](PLAN.md)).

## 1. Что нужно установить

| Что | Зачем | Как |
|---|---|---|
| Node.js 22 | всё приложение (`.nvmrc`) | `nvm use` или установщик с nodejs.org |
| pnpm 10 | менеджер пакетов | `corepack enable` (версия берётся из `package.json`) |
| Docker | PostgreSQL 16 и Redis для разработки | Docker Desktop / Docker Engine + Compose v2 |
| make | короткие команды | есть в Linux/macOS; в Windows — через WSL |

Docker можно не ставить, если у вас уже есть PostgreSQL 16 и Redis: см. §8.

## 2. Быстрый старт

```bash
git clone <репозиторий> && cd MediaRadar
make dev
```

`make dev` сам: создаёт `.env` из `.env.example`, ставит зависимости, поднимает PostgreSQL и Redis в Docker, применяет миграции, загружает аккаунты и **реестр из 16 реальных источников Алтайского края** (если база пустая) и запускает API, воркер и портал. Воркер сразу начинает собирать материалы: за первые минуты лента и дашборд наполняются настоящими новостями, дальше сбор идёт по расписанию (каждые 10–30 минут на источник), новые материалы появляются на экране сами (Live).

Если вы запускали проект раньше (в базе синтетические данные) — выполните `make db-reset`: начнёт с чистого листа и реальных источников. Синтетические данные для демонстрации без интернета и для e2e-тестов: `make db-demo` (и `DEMO_LIVE=true` в `.env` для потока «прилетающих» материалов).

- Портал: <http://localhost:3000>
- Документация API (Swagger): <http://localhost:4000/docs>
- Проверки: `GET :4000/healthz`, `GET :4000/readyz` (БД + Redis), `GET :4000/metrics` (Prometheus; в production только с токеном)

**Если порт занят другим проектом.** Порты задаются в `.env`: `WEB_PORT` (портал, 3000), `API_PORT` (API, 4000), `POSTGRES_PORT` (5432), `REDIS_PORT` (6379). Поменяйте нужный и перезапустите `make dev`; адрес портала для проверки Origin и адрес API для проксирования вычисляются из портов сами. Для PostgreSQL и Redis после смены порта поправьте ещё и адреса в `.env` (`DATABASE_URL`, `WORKER_DATABASE_URL`, `MIGRATE_DATABASE_URL`, `REDIS_URL`). Если `.env` создан старой версией проекта, удалите его (`rm .env`) и выполните `make setup` — база и данные не затрагиваются.

**Без `make` (например, Windows без WSL)** — те же шаги по одному:

```bash
git clone -b claude/tender-euler-xn20eh https://github.com/wmfbb/MediaRadar.git && cd MediaRadar
pnpm install
cp .env.example .env            # в Windows: copy .env.example .env
docker compose -f deploy/docker-compose.dev.yml up -d --wait
pnpm db:migrate
pnpm db:seed --if-empty
pnpm dev
```

Обновить код позже: `git pull`, затем `pnpm install` и `pnpm db:migrate`.

## 3. Команды

`make help` показывает полный список. Основное:

| Команда | Что делает |
|---|---|
| `make dev` | всё сразу (см. выше) |
| `make deps-up` / `make deps-down` | PostgreSQL + Redis в Docker |
| `make deps-reset` | то же + **удаление данных** |
| `make db-migrate` | применить миграции |
| `make db-seed` | загрузить аккаунты и реальные источники, если база пустая |

| `pnpm enrich` | разметить неразмеченные материалы вручную (`--reset` — перечитать все заново) |
| `pnpm nlp:eval` | замер качества разметки на контрольных выборках |
| `make test` | все тесты (юнит + интеграционные на реальных PostgreSQL/Redis) |
| `make e2e` | тесты в браузере; нужны синтетические данные: `make db-demo`, затем `make dev` с `DEMO_LIVE=true` и `COLLECT_ENABLED=false` в `.env`; первый раз: `make e2e-install` |
| `make check` | то же, что проверяет CI: формат, линтер, типы, тесты, сборка |

## 4. Устройство репозитория

```
apps/
  api/      Fastify 5: REST + WebSocket, аутентификация, права, OpenAPI
  worker/   BullMQ-воркер: очередь сбора (заглушка до Фазы 1), демо-поток материалов
  web/      Next.js 16 (App Router): портал; e2e-тесты Playwright в e2e/
packages/
  core/     id (UUIDv7), крипто (AES-GCM), TOTP, пароли (argon2id), конфиг, доменные константы
  rbac/     атомы прав, роли, матрица «роль → права» (источник истины для API и интерфейса)
  settings/ реестр типизированных настроек (платформа → тенант → источник → пользователь)
  db/       миграции (SQL), клиент, сид демо-данных, хранилище настроек
  ui/       дизайн-токены, компоненты, обёртка ECharts
deploy/     docker-compose (dev/prod), Dockerfile, Caddyfile
docs/       план, архитектура, спецификация, модель данных
prototype/  исходный прототип index.html — эталон дизайна
```

Внутренние пакеты отдаются как TypeScript-исходники (`exports: ./src/index.ts`), приложения собирают их в бандл (tsup для api/worker, Next для web). Отдельной сборки пакетов нет.

## 5. Сбор данных (Фаза 1)

Устройство и правила — в [ARCHITECTURE](ARCHITECTURE.md); здесь — как это работает сейчас.

- **Реестр источников** — `packages/db/src/seed/real-sources.ts`: 16 источников, подобранных по рейтингу «Медиалогии» и проверенных вживую. У каждого — настройка сбора (хранится версиями в `source_configs`): `rss` (адрес ленты) или `html_list` (страница-список, шаблон ссылок на материалы, при необходимости селектор даты). Добавить источник = добавить запись в реестр и выполнить `pnpm db:seed --sources-only`; настройки, изменённые человеком, при этом не перезаписываются.
- **Воркер** (`apps/worker/src/collector`): раз в минуту выбирает источники, которым пора на опрос (интервал из `cron`, при ошибках отступает ×2 до ×16, не дольше 6 часов), читает ленту/список, для новых страниц берёт заголовок, лид, дату и картинку (OpenGraph, JSON-LD, селектор из настроек), сохраняет **минимум** и шлёт свежее (за 6 часов) в Live-канал подписанных тенантов.
- **Дедупликация:** уникальность по (источник, канонический адрес); адрес приводится к общему виду (https, без www, без меток `utm_*`, якорей и хвостового слэша).
- **Удаление на источнике:** запись не удаляется никогда. Проверки наличия — через 1 ч, 6 ч, 1 сутки, 3 суток и 7 суток после сбора: «страница не найдена» (404/410/451) или перенаправление с глубокого адреса на главную → `source_state = removed`, `removed_at` (первое обнаружение, не стирается), `removal_evidence` (код ответа, адрес, время). Вернулся — `available` + `restored_at`. Исчезновение из RSS-ленты и сбои сети удалением не считаются.
- **Безопасность запросов:** только публичные http(s)-адреса, проверка IP после DNS на каждом перенаправлении, лимиты по времени (15–20 с), размеру (3–5 МБ) и числу перенаправлений, честный User-Agent `MediaRadarBot`. Если запросы идут через прокси (облачная среда разработки), имена разрешает прокси.
- **Картинки** не копируются: хранится ссылка, портал подтягивает её при показе, при недоступности показывает свою заглушку (политика CSP разрешает `https:`-картинки).
- **Ограничения:** даты без часового пояса считаются местными (+07:00); тональность, темы, персоны и организации определяются упрощённо, по словарям (см. §5а); сайты с защитой от ботов и JS-рендерингом, Telegram/VK/YouTube — позже.
- **Облачная среда разработки Claude:** исходящие запросы идут через прокси, поэтому воркеру нужен `NODE_USE_ENV_PROXY=1` (и `NODE_EXTRA_CA_CERTS`); на обычном компьютере или сервере это не требуется.

## 5а. Разметка: тема, тональность, персоны и организации (Фаза 3, упрощённая)

Без нейросети и без ключей: всё считается по словарям и правилам на самом сервере. Это упрощённая версия — она нужна, чтобы увидеть, как система работает; путь «Б» (нейросеть по ключу) описан в [PLAN.md](PLAN.md), Фаза 3Б.

- **Что получает каждый материал:** одна тема из 7 (или «без темы»), тональность — одна из 5 градаций и число от −1 до +1, список персон и организаций. Градации по порогам из `packages/core` (`SENTIMENTS`): ≥ 0,6 очень позитивная, ≥ 0,2 позитивная, ≥ −0,2 нейтральная, ≥ −0,6 негативная, ниже — критическая.
- **Когда размечается.** Сразу при сборе (в Live материал приходит уже с темой и тональностью) и плановой очередью `enrich` раз в минуту — она подбирает всё неразмеченное, включая «архив» после обновления. Включено по умолчанию; выключить: `ENRICH_ENABLED=false` в `.env`.
- **Где лежат правила** — `apps/worker/src/enrich/`: `sentiment.ts` (слова с весами от −4 до +3; «не»/«без» меняют знак; повтор слова почти не добавляет; заголовок весит больше лида), `topics.ts` (ключевые слова по темам; новости про войну и международную политику уходят в «без темы», чтобы не попадать в «Госуправление» из-за упоминания президента), `entities.ts` (поиск по словарю с падежными окончаниями и по шаблонам).
- **Словарь персон и организаций** — `packages/db/src/seed/real-entities.ts` (сейчас 19 персон и 42 организации; имена и должности проверены по собранным материалам). Персоны ищутся только из словаря (фамилия или «Имя Фамилия» в любом падеже, первая буква заглавная); случайные ФИО не собираются. Организации: словарь плюс шаблоны «ООО «…»» и «Администрация <город/район>». Добавить запись = дописать в файл и перезапустить воркер (он обновляет словарь при каждом старте). Чтобы перечитать уже размеченные материалы с новым словарём: `pnpm enrich --reset`.
- **Версия разметчика** хранится у материала (`articles.nlp_method`, сейчас `rules-1`) вместе со временем (`nlp_at`). Синтетические демо-материалы помечены `demo` и разметчиком не трогаются.
- **Ручная правка.** `PATCH /v1/admin/articles/:id/labels` с телом `{topic?, sentiment?}` (тема — ключ `agro`/`fuel`/`gov`/`food`/`city`/`econ`/`soc` или `null`) — только для ролей платформы (`platform:sources`: администратор и «куратор данных»), с записью в аудит. Исправленный материал закрывается «замком» (`labels_locked`): пересчёт не меняет ему тему и тональность (персоны и организации обновляются). `{reset: true}` снимает замок и возвращает материал в очередь. Правка относится к общему слою: её видят все тенанты, поэтому правка меток из кабинета тенанта не предусмотрена; интерфейса для правки пока нет — только API (см. Фазу 3Б).
- **Подключение нейросети («Б»).** Разметчик — это интерфейс `Analyzer` (`apps/worker/src/enrich/types.ts`): получает заголовок и лид, возвращает тему, тональность и сущности. Нейросетевой разметчик — вторая реализация с тем же результатом, регистрируется в `ANALYZERS` (`rules.ts`); очередь, запись в БД, замок правок, Live и интерфейс менять не придётся. `nlp_method` отличает метки правил от меток нейросети.
- **Качество измеряется, а не обещается.** Две выборки, размеченные вручную (`apps/worker/test/fixtures/`): `gold.json` — 130 материалов, по ним настраивались словари; `gold-fresh.json` — 70 других материалов, словари по ним не настраивались. Запуск: `pnpm nlp:eval`. Тест `enrich-gold.test.ts` не даёт ухудшить качество правкой словарей (пороги чуть ниже измеренного).

| Показатель | Выборка настройки (130) | Чистая проверка (70) |
|---|---|---|
| Тема, точность | 91 % | 61 % |
| Тональность, 5 градаций, точность | 60 % | 53 % |
| Тональность, ошибка не больше чем на одну градацию | 99 % | 97 % |
| Тональность, негатив / нейтрально / позитив, macro-F1 | 0,73 | 0,63 |
| Персоны, F1 | 0,97 | 1,00 (4 материала с персонами) |
| Организации, F1 | 0,97 | 0,96 |

  Как это читать: для чистой выборки цифры честные, для выборки настройки — завышены. Тема и тональность на правилах умеренные (целевое macro-F1 ≥ 0,70 из PLAN относится к нейросетевому варианту); персоны и организации находятся хорошо, но только те, что есть в словаре, — полнота за пределами словаря не измерялась. Обе выборки размечал разработчик (ИИ), а не независимые эксперты, поэтому метки стоит просмотреть владельцу или аналитику; чем больше ручных исправлений, тем точнее будет оценка.
- **Ограничения.** Иронию, сарказм и сложные фразы правила не понимают; тональность отражает «окраску слов» (авария — негатив, награда — позитив), а не отношение к конкретной персоне или организации; для материала нет объяснения «почему такая тональность»; персон за пределами словаря не находит; географическая привязка и пересказы — Фаза 3Б.

## 6. Правила, которые нельзя нарушать

### 6.1 База данных и изоляция тенантов

- Миграции — обычные SQL-файлы в `packages/db/migrations/NNNN_название.sql`. Применённую миграцию **не редактируют** (проверяется контрольная сумма) — только новая миграция сверху.
- Приложение ходит в БД ролями `app_api` / `app_worker` без права обхода RLS. Владелец схемы (`MIGRATE_DATABASE_URL`) — только для миграций и сидов.
- На каждой таблице тенанта включены `ENABLE` + `FORCE ROW LEVEL SECURITY`. Новая таблица с данными тенанта: вызвать в миграции `SELECT app_rls_tenant_table('имя');` (и в конце `SELECT app_apply_grants();`), а затем **добавить её в классификацию** в `packages/db/test/rls.test.ts` — тест «все таблицы классифицированы» упадёт, пока этого не сделано, и тест изоляции для таблицы появится автоматически.
- Контекст запроса передаётся переменными сессии `app.tenant_id`, `app.user_id`, `app.platform_admin`, `app.system` — только через `db.tenant(...)`, `db.platform(...)`, `db.system(...)` из `packages/db/src/client.ts`.
- Внутри одной транзакции запросы выполняются **последовательно** (одно соединение): параллельный `Promise.all` по одному клиенту `pg` запрещён.

### 6.2 API и права

- Каждый маршрут обязан объявить доступ: `access.public()`, `.session()`, `.account()`, `.user()`, `.tenant('право')` или `.platform('право')`. Тест `permissions.test.ts` падает, если маршрут объявлен без доступа.
- Право — это атом в `packages/rbac`; интерфейс только скрывает ненужное, **решение всегда принимает сервер**. Матрица «роль × право» закреплена тестом по `PRODUCT_SPEC §8.2`.
- Мутации требуют CSRF-токен (`x-csrf-token` из cookie `mr_csrf`) и допустимый `Origin`.
- Ошибки — `application/problem+json`; тексты на русском.

### 6.3 Настройки

Новая настройка = запись в `packages/settings/src/index.ts` (ключ, область, схема Zod, значение по умолчанию, группа в интерфейсе). Изменения версионируются, пишутся в историю и аудит, откатываются.

### 6.4 Интерфейс

Цвета, радиусы, тени — только токены из `packages/ui/src/theme.css` (светлая и тёмная тема). Новые компоненты — в `packages/ui`, с тестом в `packages/ui/test`.

## 7. Тесты

- `pnpm test` (или `make test`) — всё. Для БД-тестов нужны PostgreSQL и Redis (`make deps-up`); тестовые базы (`mediaradar_test`, `mediaradar_test_api`, `mediaradar_test_worker`) создаются и заполняются автоматически, а тесты воркера работают в отдельной логической БД Redis №15 — база и очереди разработки не затрагиваются, `make test` можно запускать при работающем `make dev`.
- E2E (`make e2e`) идёт против запущенного стека и меняет состояние демо-данных: сценарий 2FA включает и затем отключает двухфакторную защиту у `o.timoshina@altai.media`. Если прогон оборвать посередине, выполните `make db-reset`.
- На вход действует лимит 20 попыток в минуту с одного IP — e2e укладывается, но не запускайте несколько прогонов одновременно.

## 8. Наблюдаемость

Структурные JSON-логи (pino, уровень — `LOG_LEVEL`, заголовки cookie, authorization и CSRF скрываются), `GET /healthz` (процесс жив), `GET /readyz` (БД и Redis доступны), `GET /metrics` — метрики Prometheus (длительность HTTP-запросов, число WebSocket-соединений, процесс и event loop Node.js; состояние очередей BullMQ видно на дашборде и пока не экспортируется в метрики); в production требуют `Authorization: Bearer <METRICS_TOKEN>`.

## 9. Без Docker

Нужны PostgreSQL 16 и Redis на localhost. Создайте суперпользователя и базу:

```sql
CREATE ROLE mediaradar LOGIN SUPERUSER PASSWORD 'mediaradar_dev';
```

## 10. Production (черновик)

`deploy/docker-compose.prod.yml` — Caddy (автоматический HTTPS) → web + api, воркер, PostgreSQL, Redis, одноразовый сервис миграций. Все секреты обязательны (`deploy/.env.prod.example`); API в production не стартует с ключом шифрования по умолчанию и без `METRICS_TOKEN`. Это каркас: образы и compose проверялись только на уровне YAML и пошаговым воспроизведением сборки; боевая проверка и бэкапы — задача Фаз 9–10.

Снаружи через Caddy закрыты `/api/metrics` и `/api/docs`.
